## 一、延後未做的三件事

使用者在 2026-09-15 確認這三件**都先放著**。

### 1. 設定頁改版面尺寸後，拼版頁不提示重新排圖

在設定頁把某個尺寸的寬高改掉之後，拼版頁的畫布仍以**舊尺寸**繪製、分頁標籤仍顯示舊的 `sizeName`，而且沒有任何「請按排圖」的提示。

- 只有拼版頁的尺寸勾選（`state.ts` 的 `toggleSheetSize`）會設定 `LAYOUT_STALE_MESSAGE`。
- 這是**既有的不一致**而非本次引入：改「最小間距」同樣不設 stale 訊息。
- 修法需要讓設定層的變動反映到拼版層，屬跨層改動。

**歷史**：階段 3 的整枝審查提出此項並明確延到階段 4，但階段 4 的計畫本身沒有納入，因此至今未做。這是計畫的缺口，不是遺忘。

### 2. 拆分 `src/components/ImpositionCanvas.tsx`

該檔 405 行、單一 forwardRef 元件本體 **172 行**（專案慣例：函式 <50 行）。階段 4 讓它從 114 行成長到 172 行。

建議切兩刀：

- `ItemContent`／`ImpositionItem`／`SheetBoard`／`contentTransform` → `src/components/SheetBoard.tsx`
- `nextPaint`／`captureSheet`／`buildSheetsPdf`／`PDF_DPI`／`MAX_CANVAS_PX` → `src/imposition/pdfCapture.ts`

第二刀有額外好處：`src/imposition/**/*.ts` 在覆蓋率白名單內，而 `captureSheet` 的 scale 計算與 `Number.isFinite` 防護目前**完全沒有單元測試**，搬過去就測得到。拆完後 render 本體仍約 120 行；要再降得把 `exportPDF` 抽成 `useSheetPdfExport` hook。

**為何延後**：這兩刀會動到剛以變異測試逐條驗證過的程式碼，與功能修正分開做比較安全。

### 3. 抽掉 e2e 重複的前置設定

`e2e/cut-underprint-imposition.spec.ts` 有三處逐字重複約 20 行的多版面前置（進設定頁 → 新增小尺寸 → 回拼版頁 → 取消勾選 7 個預設尺寸 → 填份數 → 排圖），抽成 helper 可少約 40 行。

⚠️ 抽的時候 **`DEFAULT_SIZE_NAMES` 要維持硬編碼**，不要改成 `import { DEFAULT_SHEET_SIZES }`。改了會變成用實作驗證實作：若某個預設尺寸的核取方塊 testid 拼錯或沒渲染，名單會自動同步而測不出差異。硬編碼在預設清單異動時失敗，那是有意義的提醒。

## 二、已定案的效能數字（勿重新猜測）

PDF 多頁匯出，本機 headless chromium 實測：

| 情境 | 10 張版面 | 50 張版面 |
|---|---|---|
| 小圖（400×240 px） | 1,176 ms | 7,125 ms |
| 大圖（2400×1600 px，每張版面掛一件全解析度圖） | 2,322 ms | 12,835 ms |

耗時**呈線性**（每張 118–257 ms）。計畫設定的門檻是「10 張超過 30 秒才需提出」，實測差兩個數量級。

**結論：不改掛載策略（匯出時一次把所有版面掛上畫面外暫存區）、不加版面數上限**（維持既有 `MAX_SHEETS = 50`）。

**這組數字沒有涵蓋的**：記憶體峰值（只量了牆鐘時間）、單張版面塞滿多件大圖、行動裝置或低記憶體機器。

若日後有人主張改成「分批掛載」以降低尖峰記憶體——**請先量出數字再改**。當初審查建議分批時沒有數字，量完才發現沒有必要。

## 三、覆蓋率百分比看不出的盲點

- 階段 4 新增的 `SheetBoard`、PDF 畫面外暫存區、`captureSheet`、`buildSheetsPdf` **全在 `src/components/`，不在覆蓋率白名單內**。它們的保障 100% 來自 e2e，而不是那個 94.49% 的全域數字。
- 「有被執行但沒有被斷言」的程式碼會讓覆蓋率好看卻毫無保障。`sheetsWithContent` 的 `layerIds.has(...)` 一度如此——把它改成恆真，292 個單元測試沒有任何一個會失敗（後來補了直接測試）。

判斷保障程度時，**用變異測試（把實作改壞，確認恰好只有對應測試失敗）比看覆蓋率百分比可靠**。本次所有關鍵防護都以此方式驗證過。

## 四、只能靠人眼確認的 PDF 行為

以下五項 e2e 涵蓋不到（需要 PDF parser 或肉眼），**尚未驗證**：

1. PDF 頁數是否等於版面數
2. 每頁紙張尺寸是否符合該版面（在閱讀器看文件屬性）
3. 匯出過程畫面是否閃爍或跳動
4. 畫布縮放改成 25% 再匯出，解析度是否與 100% 時相同
5. 匯出期間 Toast 是否顯示「正在產生 PDF：N / M 頁」

e2e 已涵蓋的是：下載確實觸發、檔名為 `imposition-layout.pdf`、畫面外暫存區在匯出結束後從 DOM 移除、連點兩次只產生一次下載、匯出途中切換分頁仍會完成。

## 五、接受並記錄的結構性殘留（非缺陷）

- **舊 localStorage 裡的重名尺寸擋不掉**。UI 有兩條唯一化路徑（新增自動避名、改名撞名還原），但只擋**新產生**的重名。若使用者的設定從舊版或手動編輯而來、已含重名，`ImpositionPanel` 會出現重複 React key 與重複 testid，且兩者共用同一個勾選狀態（`disabledSizeNames` 以名稱為鍵）。
  **刻意如此**：若在 `sheetSizeSchema` 加唯一性約束，一份含重名的既存設定會讓 `parseSettings` 整包失敗 → 退回預設 → **使用者的 remove.bg API key 被無聲清空**。保住 API key 比擋掉這個邊緣情況重要。

- **刪除某尺寸後再新增同名尺寸，會沿用舊的停用狀態**。`uniqueNewSheetSizeName` 只看設定清單，看不到拼版頁的 `disabledSizeNames`，兩層刻意解耦。使用者一鍵可勾回，且已補上「全部停用時顯示原因」的提示，不會再出現「排圖是灰的卻不說為什麼」。

- **空版面時版面框位置略為下移**。空狀態提示從版面框內搬到框外（必要改動——否則「尚無排版項目」會被截進 PDF），置中容器因此多了一個子節點。只影響沒有任何項目時的畫面。

## 六、尚未決定的專案層級事項

本專案**沒有安裝 `@types/react`**，`tsconfig` 也沒開 `strict`，因此 JSX props 實際上不受型別檢查（已實證：刪掉必要 prop 或傳入錯誤型別都能通過 typecheck）。

實務影響：`key` 不能直接寫在自訂元件上（會報 `Property 'key' does not exist`），全專案統一改用 `<React.Fragment key={...}>` 包一層。

此事已向使用者提出，尚未決定，不主動重提。
